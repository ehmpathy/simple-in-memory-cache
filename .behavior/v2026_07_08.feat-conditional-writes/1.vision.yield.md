## the outcome world

### day-in-the-life

today, `simple-in-memory-cache` is a plain key→value store with time-based expiry. it can
tell you *what* is stored, but not *whether the thing you last saw is still the thing stored*.
that gap makes it unsafe for any "only-if" write — the class of operations at the heart of
locks, leases, and stampede control.

after this wish, the same tiny cache gains a third question it can answer — **"what version
is this key at?"** — and two new promises on writes:

- **put-if-absent** — "write only if nobody else has claimed this key"
- **compare-and-set** — "write only if the value is still the one I last read"

that is exactly the primitive `with-simple-mutex` needs to build a per-process mutex on top of
an in-memory cache: `acquire = put-if-absent`, `release = compare-and-delete on our version`.

### before / after

```ts
// ── before ────────────────────────────────────────────────
const cache = createCache<string>();
cache.set('lock:report', 'worker-a');       // unconditional — clobbers anyone
cache.set('lock:report', 'worker-b');        // silently overwrites worker-a. no safety.
// two workers both "hold" the lock. race lost, silently.

// ── after ─────────────────────────────────────────────────
const cache = createCache<string>();

// worker-a claims the lock (put-if-absent: version null)
cache.set('lock:report', 'worker-a', { condition: { version: null } }); // ✓ wins
const myVersion = cache.version('lock:report');   // 'v1' — the token i now hold

// worker-b tries to claim the same open key
cache.set('lock:report', 'worker-b', { condition: { version: null } });
// ✋ throws SimpleCacheConditionError — key was not absent. worker-b knows it lost.

// worker-a later renews — CAS against the version it ACQUIRED, not a fresh read
cache.set('lock:report', 'worker-a', { condition: { version: myVersion } }); // ✓ still mine
// ✋ if worker-b had taken over, the token would be 'v2' — this throws, no clobber
```

> ⚠️ **subtle but critical**: the CAS token must be the one captured at **acquire** time (`myVersion`),
> not a fresh `cache.version()` read taken right before the set. in the single-threaded in-memory tier,
> a fresh read always returns the *current* token, so `{ version: <fresh read> }` always matches and
> guards **no state at all**. the whole point of CAS is to compare against a *prior observation*.

### the "aha"

the value clicks the moment two callers race the same open key and **exactly one wins, loudly**.
the loser does not get a silent overwrite — it gets a `SimpleCacheConditionError` it can catch
and branch on. the cache stops being a dumb bag of bytes and becomes a *coordination primitive*.

### the core insight — a condition compares against a *prior observation*

this is the mental model that makes the whole contract click. **you cannot form a CAS condition without
a prior observation of the key** — a version token is opaque and unforgeable, so the *only* way to hold
one is a prior `get` / `version` / acquire. that gives a clean rule for which condition is even
*meaningful*:

| what you hold | the only meaningful condition | what you're really asking |
|---------------|-------------------------------|---------------------------|
| **no** prior observation | `version: null` (put-if-absent) | "is this key still **unclaimed**?" |
| an **ownership** token (from acquire) | `version: token` (CAS) | "is this lock still **mine**?" — value irrelevant |
| a **value** + its token (from get) | `version: token` (CAS) | "is the value i **acted on** still current?" |

so `version: token` is *always* tied to a prior observation — but that observation is sometimes a
**value** (optimistic concurrency) and sometimes just **ownership** (mutex). they are different needs
that share one mechanism:

- **value observation** → you care about the prior get value. read value + version, compute from the
  value, write-back guarded on that version. (see "version-checked get" below — the star of this usecase.)
- **ownership observation** → you do **not** care about the stored value (it's your own worker-id). you
  hold `v1` from acquire and CAS-delete on `v1`; the version match alone proves no one else took the lock.
  this is the case that is pure-CAS yet **not** about the value — the counterexample to "CAS only matters
  if you care about the value."

put-if-absent (`version: null`) is the odd one out: it needs **no** prior observation, because "is it
absent?" is answerable without a prior sight of the key. if you don't care about a prior get value and
you're not tracking ownership, `version: null` is the *only* condition that carries meaning.

## user experience

### usecases & goals

| usecase | goal | mechanism |
|---------|------|-----------|
| per-process mutex (`with-simple-mutex`) | one holder at a time | `acquire` = put-if-absent; `release` / `renew` = CAS on the **acquired** version (value irrelevant) |
| stampede / compute-once | only the first misser computes | put-if-absent guards the compute slot (no prior observation needed) |
| optimistic concurrency | act on a value, don't clobber a fresher one | **version-checked get** (read value + version atomically) → compute → **version-guarded set** on that same version |

### contract inputs & outputs

three touch points on the cache api (all **additive** — every prior call still compiles and
behaves identically):

1. **`version(key)` — new reader**
   ```ts
   version: (key: string) => string | undefined;
   ```
   returns the current opaque version token for a live key, or `undefined` when the key is
   absent or expired. token is **equality-only** — never parsed, never ordered.

2. **`get(key, options)` — widened → the version-checked get (⭐ the star of optimistic concurrency)**
   ```ts
   get: (key: string, options?: { condition?: { version: string | null } }) => T | undefined;
   ```
   with a `condition`, verify the stored version **before** returning the value; on mismatch throw
   `SimpleCacheConditionError`. this fuses "read the value" and "assert it is still the version i expect"
   into **one** call:
   ```ts
   const current = cache.get('counter', { condition: { version: v } });
   // ✓ returns the value IF it is still at version v
   // ✋ throws SimpleCacheConditionError if the version drifted — the value you were about to act on is stale
   ```
   why it matters: it is the atomic "give me the value, but only if it is the one i last saw" primitive.
   without it, a caller would `version()` then `get()` as two steps and have to reason about drift between
   them; the version-checked get collapses that into a single guarded read.

3. **`set(key, value, options)` — widened, condition ordered *after* expiration**
   ```ts
   set: (
     key: string,
     value: T | undefined,
     options?: { expiration?: IsoDuration | null; condition?: { version: string | null } },
   ) => void;
   ```
   - `condition.version: null`   → put-if-absent (write only if no live entry)
   - `condition.version: '<tok>'` → compare-and-set (write only if stored version === tok)
   - on a precondition miss → throw `SimpleCacheConditionError`.

### what leveraging it looks like (test-drive) — three patterns

**pattern 1 — put-if-absent (no prior observation needed): claim, converge on the winner**
```ts
const claim = (key: string, who: string) => {
  try {
    cache.set(key, who, { condition: { version: null } });   // write only if unclaimed
    return { held: true, by: who };
  } catch (error) {
    if (error instanceof SimpleCacheConditionError) return { held: false, by: cache.get(key) };
    throw error;
  }
};
```

**pattern 2 — ownership CAS (observe = acquire; value irrelevant): mutex renew / release**
```ts
// acquire mints my handle; i keep it
cache.set('lock:report', me, { condition: { version: null } });
const myVersion = cache.version('lock:report');   // 'v1' — my ownership token

// renew — guard on the version i ACQUIRED (not a fresh read)
cache.set('lock:report', me, { condition: { version: myVersion } });     // ✋ throws if not still mine

// release — compare-and-delete on the version i hold
cache.set('lock:report', undefined, { condition: { version: myVersion } }); // ✋ throws if someone else took it
// note: value ('me') is never inspected — only the version proves ownership
```

**pattern 3 — value CAS (observe = the value itself): optimistic read-compute-write**
```ts
// ⭐ version-checked get: read the value AND its version together, atomically
const version = cache.version('counter');
const current = cache.get('counter', { condition: { version } }); // ✋ throws if it drifted mid-flight

// …derive a new value FROM the value i observed…
const next = (current ?? 0) + 1;

// write-back guarded on the SAME version i read → a slow writer cannot clobber a fresher value
cache.set('counter', next, { condition: { version } });
// ✋ SimpleCacheConditionError → someone moved 'counter' since i read it; my `current` was stale, so retry
```
here the whole point is the **prior get value** — `next` is computed from `current`, and the condition
guarantees the value i acted on is still the current one at write-back. this is the usecase the
version-checked get exists for.

### timeline

read → decide → conditional write → (win | `SimpleCacheConditionError`). single synchronous
tick — no awaits, no scheduler; the whole point of the in-memory tier is that the read-check-write
is atomic *because* the runtime is single-threaded and the op never yields.

## mental model

- **to a friend**: "it's a cache that also does 'only write if you're sure' — like a git push
  that fails if someone else pushed first."
- **analogies**: optimistic-lock row `version` column; HTTP `If-Match` / ETag; a compare-and-swap
  (CAS) CPU instruction; `SETNX` in redis (put-if-absent).
- **terms**:

| users say | we say |
|-----------|--------|
| "lock" / "claim" | put-if-absent (`condition.version: null`) |
| "only if unchanged" | compare-and-set (`condition.version: token`) |
| "read it, but only if it hasn't changed" | version-checked get (`get(k, { condition: { version } })`) |
| "the tag / etag / stamp" | version token (opaque, equality-only) |
| "it failed the check" | `SimpleCacheConditionError` (a `ConstraintError`, exit 2) |

- **the closest analogy for the version-checked get is HTTP `If-Match`**: "GET me this resource, but
  only if its etag is still the one i hold — otherwise tell me it moved." same shape: read guarded by a
  version you observed before.

## evaluation

### how well it solves the goals

- unblocks `with-simple-mutex` per-process tier directly (put-if-absent = acquire).
- solves stampede (first-misser-computes) with the same primitive.
- solves optimistic concurrency (version-guarded set).
- structurally satisfies `WithCacheConditionals<SimpleCacheSync<T>>` from the shipped 0.17.0
  contract, so any consumer that requires the capability accepts our cache with zero glue.

### pros

- **purely additive** — no prior signature changes behavior; `condition` is optional and
  defaults to unconditional. every current test still passes untouched.
- **atomic for free** — single-threaded js makes read-check-write inherently atomic in-memory;
  no locks, no CAS loop needed.
- **opaque token** keeps us free to change the token scheme (counter → uuid) later.
- **no dependency cycle** — the contract is pulled in **types-only** (see decision below), so
  nothing is added to the runtime graph.

### cons / tradeoffs

- we must mint & store a version token per entry — a small per-key memory cost.
- the token scheme is an internal invariant we must never leak semantics of (equality-only).
- **error-class identity** — our `SimpleCacheConditionError` is a *local* class (the wrapper's
  is a distinct value we cannot import without a cycle). name+shape identical, identity distinct.
  in scope for #19 this is fine; it only matters for the wrapper's `exception: 'ignore'` converge
  path — tracked as the one open item below.

### edgecases → pit of success

| edgecase | contract keeps you safe by… |
|----------|------------------------------|
| expired entry, then put-if-absent | expiry treated as absent → put-if-absent **succeeds** (version of an expired key is `undefined`) |
| two put-if-absent on one open key | version check runs before the write on each → exactly one wins, other throws |
| CAS with a stale token | `found !== condition.version` → throws, never clobbers |
| CAS against an absent key | `found` is `undefined`, token is a string → mismatch → throws (can't CAS what isn't there) |
| `set(key, undefined, { condition })` (conditional delete) | condition checked *before* delete → `with-simple-mutex` release (compare-and-delete) works |
| unconditional set on a versioned key | mints a **fresh** token → any outstanding CAS token is now stale (correct) |

## open questions & assumptions

### ✅ decided — no cycle: types-only peer dependency + local error class (path A)

`with-simple-cache@0.17.0` **depends on `simple-in-memory-cache@0.4.2`** (its `package.json`
line 68). a **runtime** dep back on `with-simple-cache` would form a package cycle. we avoid it:

- **contract types** — pulled in **types-only** via `import type { … }` from `with-simple-cache`,
  declared as a **peerDependency**. type imports are erased at compile → **zero runtime edge, no
  cycle**. `with-simple-cache`'s `SimpleCache.ts` imports only `iso-time`, so there is no
  *type-level* back-reference to us either. this fully satisfies the typecheck acceptance
  (`the cache satisfies WithCacheConditionals<SimpleCacheSync<T>>`).
- **error class** — `SimpleCacheConditionError` is a runtime **value** (thrown + `instanceof`-ed),
  so it cannot ride a types-only import. we **define it locally**: `extends ConstraintError` from
  `helpful-errors` (**already a dependency**, package.json L70), with the same
  `{ key, condition, found }` metadata and the same two messages the shipped class uses.

```
peerDependency: with-simple-cache          # published contract — consumers supply it
devDependency:  with-simple-cache          # ALSO required — peer deps are not installed for our own
                                           #   test:types, so the conformance typecheck needs it locally
import type { WithCacheConditionals, SimpleCacheSync, SimpleCacheCondition } from 'with-simple-cache';  // erased
class SimpleCacheConditionError extends ConstraintError<{ key; condition; found }> {}  // local value, no cycle
```

> **note (peer + dev)**: `with-simple-cache` must be declared in **both** `peerDependencies` (the published
> contract — the consumer already has it) **and** `devDependencies`. npm/pnpm do not install a package's own
> peerDependencies into its node_modules, so without the devDependency our `satisfies WithCacheConditionals<…>`
> typecheck could not find the types in CI. this is install-only; the import is still types-only and erased,
> so there is still **no runtime edge and no cycle**.

#### ✅ revised by wisher (2026-07-16) — dev-only, drop the peerDependency

the peer + dev plan above is **superseded**. the wisher decided **dev-only**: declare `with-simple-cache`
solely as a `devDependency`, with **no** `peerDependency`.

- **wisher quote (2026-07-16)**: "dev only is great".
- **why it holds**: the peerDependency's only job was to signal "the consumer supplies this". but every
  consumer that requires `WithCacheConditionals<SimpleCacheSync<T>>` already depends on `with-simple-cache`
  **directly** (that is where the type lives), so a peerDependency here is redundant — it re-declares a
  dependency the consumer already owns. the devDependency alone still satisfies the local conformance
  typecheck (the types are present in our own node_modules for CI), and the import stays types-only and
  erased — so the cycle-avoidance property is unchanged.
- **net**: still **no runtime edge, no cycle**; one fewer redundant dependency declaration. the code and
  `package.json` reflect this dev-only decision; the peer + dev text above is kept for the audit trail of
  how the decision evolved.

## what is awkward?

- **the inverted arrow** — the vocabulary (types + error) lives in `with-simple-cache`, which
  already depends on us; borrowing from it at runtime would invert the dependency. types-only
  dodges this cleanly, but it forces a *second* `SimpleCacheConditionError` class into the
  ecosystem — name-identical, identity-distinct — a latent trap for anyone who does
  `instanceof theWrapper'sError` on our throw. path C would heal it; for now it is a documented seam.
- **`never` as the base condition slot** reads as a hack on first encounter — but it is load-bearing
  (contravariant assignability under `strictFunctionTypes`). we conform, not question.
- **conditional delete** (`set(key, undefined, { condition })`) is where put-if-absent's mental
  model strains: "put-if-absent" on a delete is odd phrasing, yet it's exactly what mutex-release
  (compare-and-delete) needs. the shipped example checks the condition before the `undefined`
  branch, so we follow suit — but the naming will make a reader pause.
- **opaque-but-a-counter** — the token is documented as equality-only/opaque, yet a `v1/v2`
  counter visibly *looks* orderable. correct behavior, mildly misleading appearance. a uuid would
  hide the ordering but costs entropy for no functional gain given node>=8.
